# Feature Specification: Unused Search Scope Cleanup

**Feature Branch**: `004-unused-scope-cleanup`

**Created**: 2026-09-22

**Status**: Draft

**Input**: User description: "GAP-008 잔여 해소 — 닫힌 탭이 남긴 죽은 검색 스코프(query_key)의 멤버십을 사용자가 선택적으로 정리할 수 있게 한다. 고아 기사 행은 유지하고 건수만 보고한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 죽은 검색 범위 미리보기와 정리 (Priority: P1)

탭을 자주 만들고 지우는 사용자는 통계 화면의 "저장소 지표"에서 현재 검색 범위 수와 그중 **사용하지 않는(열린 탭이 없는) 범위 수**를 본다. "사용하지 않는 범위 정리"를 실행하기 전에 정리 대상 범위 목록과 삭제될 소속 정보 건수를 미리보기로 확인한 뒤, 확인을 눌러 정리한다. 정리 후에는 삭제된 소속 건수, 남은 범위 수, 소속이 없어진(고아) 기사 건수를 결과로 확인한다.

**Why this priority**: GAP-008의 핵심 가치(죽은 스코프 누적에 대한 사용자 가시성 + 선택적 정리 수단)를 직접 제공한다. 이 스토리만으로 감사 권고 12의 절반(지표 노출은 이미 있음)과 정리 수단이 완성된다.

**Independent Test**: 열린 탭 1개(범위 A)와 닫힌 탭이 남긴 범위 B·C가 있는 상태에서 통계 화면을 열어 범위 B·C가 정리 대상으로 표시되는지 확인하고, 정리를 실행한 뒤 범위 A의 기사 목록이 그대로인지 확인하면 독립 테스트가 된다.

**Acceptance Scenarios**:

1. **Given** 열린 탭이 없는 범위 B에 소속 정보 120건이 있고 범위 A 탭이 열려 있을 때, **When** 사용자가 정리 미리보기를 열면, **Then** 대상 범위로 B가 표시되고 예상 삭제 소속 120건이 표시된다.
2. **Given** 미리보기에서 대상이 확인된 상태에서, **When** 사용자가 정리를 확정하면, **Then** 범위 B의 소속 정보가 모두 삭제되고 결과에 삭제 120건·남은 범위 수·고아 기사 건수가 표시된다.
3. **Given** 죽은 범위가 하나도 없을 때, **When** 사용자가 정리를 시도하면, **Then** 삭제 없이 "정리할 범위가 없음" 취지의 zero 보고가 반환된다(버튼 비활성화 또는 실행 후 zero 보고 중 택1).

### User Story 2 - 열린 탭과 공유 기사는 절대 영향 없음 (Priority: P1)

정리 대상 범위에 속한 기사 중 열린 탭의 범위에도 함께 속한 기사가 있다. 정리를 실행해도 열린 탭의 기사 목록, 읽음/북마크 상태, 중복 표시는 그대로이며, 열린 탭 자체의 범위는 정리 대상에 절대 포함되지 않는다.

**Why this priority**: 정리 기능의 안전 계약이다. 이 보장이 없으면 사용자는 정리 실행을 두려워하고 기능이 무용지물이 된다.

**Independent Test**: 기사 X를 범위 A(열린 탭)와 범위 B(죽은 범위)에 함께 소속시킨 뒤 정리 실행 후, 범위 A 목록에 기사 X가 동일한 읽음·북마크·tag 상태로 남아 있으면 독립 테스트가 된다.

**Acceptance Scenarios**:

1. **Given** 기사 X가 열린 범위 A와 죽은 범위 B에 모두 속할 때, **When** 정리를 실행하면, **Then** 범위 A의 소속 정보는 남고 범위 B의 소속 정보만 삭제되며 기사 X는 범위 A 목록에 그대로 표시된다.
2. **Given** 열린 탭들의 범위 집합이 A·D일 때, **When** 정리를 실행하면, **Then** A·D는 대상 목록에 나타나지 않고 삭제 건수에도 포함되지 않는다.
3. **Given** 정리 실행 전후로 열린 탭의 목록을 비교할 때, **When** 기사 집합·읽음·북마크·태그를 대조하면, **Then** 모두 동일하다.

---

### User Story 3 - 실행 중인 수집/유지보수와의 상호 배제 (Priority: P2)

뉴스 수집(fetch)이 실행 중이거나 DB 유지보수 모드가 활성일 때 정리를 시도하면 작업이 거부되고 이유가 안내된다. 수집이 끝난 뒤 다시 실행하면 정상 동작한다.

**Why this priority**: 수집 중 DB 쓰기와 정리 쓰기가 겹치면 소속 정보가 어긋날 수 있다. 기존 유지보수 흐름의 상호 배제 원칙(활성 워커가 끝나야 진입)과 동일 선상이다.

**Independent Test**: 수집 실행 중에 정리를 시도해 거부되는지, 수집 완료 후 정리가 성공하는지 확인하면 독립 테스트가 된다.

**Acceptance Scenarios**:

1. **Given** 수집 워커가 실행 중일 때, **When** 사용자가 정리를 시도하면, **Then** 정리가 실행되지 않고 진행 중 작업이 있다는 취지의 안내가 표시된다.
2. **Given** 유지보수 모드가 활성일 때, **When** 사용자가 정리를 시도하면, **Then** 정리가 실행되지 않는다.
3. **Given** 진행 중 작업이 없을 때, **When** 사용자가 정리를 실행하면, **Then** 정상적으로 미리보기·확정 흐름이 진행된다.

---

### User Story 4 - 정리 결과의 정합성과 재실행 안정성 (Priority: P2)

정리 직후 통계 화면의 수치(전체 기사 수·범위 수)가 실제와 일치하고, 남은 범위의 중복 표시가 정확하며, 정리 직후 다시 정리를 실행하면 삭제 0건의 no-op 보고가 나온다.

**Why this priority**: 수치 불일치나 중복 표시 깨짐은 정리 기능 자체에 대한 신뢰를 무너뜨린다. 재실행 안정성은 반복 사용의 전제다.

**Independent Test**: 정리 전후 통계 수치를 대조하고, 남은 범위에서 중복 표시 샘플을 확인한 뒤, 정리를 한 번 더 실행해 0건 보고가 나오는지 확인하면 독립 테스트가 된다.

**Acceptance Scenarios**:

1. **Given** 정리가 완료된 직후, **When** 통계 화면을 보면, **Then** 범위 수는 실제 남은 범위 수와 일치하고 전체 기사 수는 정리 전과 동일하다(고아 기사 행 유지 정책).
2. **Given** 죽은 범위와 열린 범위에 같은 제목의 기사가 있었을 때, **When** 정리 후 열린 범위의 목록을 보면, **Then** 중복 표시가 실제 남은 소속 기준으로 정확하다.
3. **Given** 정리 완료 직후, **When** 정리를 다시 실행하면, **Then** 삭제 0건·대상 0건의 보고가 나오고 DB에 변화가 없다.

---

### Edge Cases

- 키워드 탭이 하나도 열려 있지 않을 때(유지 집합이 빔): 전체 범위가 죽은 범위가 되므로 **정리를 거부**한다. 보관 탭만으로 기사를 찾는 사용자의 목록이 한 번에 비는 사고를 막는다.
- 삭제 표시(soft-delete, 휴지통)된 기사의 소속 정보: 정리 대상에서 **제외**한다. 삭제 전파·보존 기간 정책이 해당 행을 관장하므로 정리 기능이 간섭하지 않는다.
- 정리 대상 범위에 북마크된 기사가 포함될 때: 소속 정보만 삭제하고 기사 행은 유지하므로 북마크 보기에서는 계속 보인다. 결과 보고에 이 사실이 드러나야 한다(고아 기사 건수에 포함).
- 정리 실행 중 앱 종료/충돌: 소속 삭제는 한 트랜잭션으로 묶여 전체 적용 또는 전체 롤백이어야 하며, 중간 상태가 남지 않는다.
- 동일 범위 키의 대소문자·공백 변형: 범위 동일성 판단은 저장된 정규형 키의 정확 일치로만 하며, 퍼지 매칭을 하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 통계 화면의 저장소 지표에 전체 검색 범위 수와 함께 **사용하지 않는 범위 수**를 표시해야 한다.
- **FR-002**: 정리 실행 전에 대상 범위 목록(식별 가능한 이름 포함)과 예상 삭제 소속 건수, 정리 후 소속이 없어질 기사(고아) 예상 건수를 미리보기로 보여줘야 한다.
- **FR-003**: 열린 탭이 사용 중인 범위는 정리 대상에서 항상 제외해야 한다. 유지 집합은 실행 시점에 열려 있는 탭으로부터 도출한다.
- **FR-004**: 키워드 탭이 하나도 열려 있지 않아 유지 집합이 비게 되면 정리를 거부하고 이유를 안내해야 한다.
- **FR-005**: 삭제 표시(soft-delete)된 기사에 연결된 소속 정보는 정리 대상에서 제외해야 한다.
- **FR-006**: 정리로 소속 정보가 삭제된 뒤에도 남은 범위의 중복 표시는 남은 소속 기준으로 정확해야 한다.
- **FR-007**: 수집 워커 실행 중이거나 유지보수 모드가 활성일 때는 정리를 시작하지 않고 사유를 안내해야 한다(기존 유지보수 진입 가드와 동일 원칙).
- **FR-008**: 정리 결과로 삭제된 소속 건수, 남은 범위 수, 고아 기사 건수를 보고해야 한다.
- **FR-009**: 소속이 하나도 남지 않게 된 기사(고아)의 본문 행은 삭제하지 않고 유지해야 한다. 전체 기사 수 통계는 정리 전후로 변하지 않는다.
- **FR-010**: 소속 삭제 묶음은 원자적으로 적용되어야 한다(전체 적용 또는 전체 롤백, 중간 상태 없음).
- **FR-011**: 정리 직후 동일 조건으로 다시 실행하면 삭제 0건의 no-op 보고가 나와야 한다(멱등성).
- **FR-012**: 북마크 보기에만 의존하는 기사(북마크됐으나 소속이 모두 삭제된 기사)는 북마크 보기에서 계속 열람 가능해야 한다.

### Key Entities

- **검색 범위(Search scope)**: 탭의 검색 조건을 식별하는 정규형 키와 사용자에게 보여줄 이름. 열린 탭이 있으면 live, 없으면 dead(사용하지 않음).
- **소속 정보(Membership)**: 기사가 특정 검색 범위에 속한다는 연결 기록. 정리 기능이 삭제하는 유일한 대상.
- **고아 기사(Orphaned article)**: 정리 후 어떤 범위에도 속하지 않게 된 기사 행. 본문·읽음·북마크·메모·태그는 유지되며 소속만 없다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 죽은 범위 50개·소속 10,000건 규모의 보관함에서 미리보기와 정리가 끝나고 삭제·잔여·고아 건수가 실제와 정확히 일치한다.
- **SC-002**: 정리 전후로 열린 탭의 기사 목록(구성·읽음·북마크·태그)이 100% 동일하다.
- **SC-003**: 수집 실행 중 정리 시도는 100% 거부되고, 수집 완료 후 동일 시도는 성공한다.
- **SC-004**: 사용자는 정리 실행 없이 통계 화면만으로 사용하지 않는 범위의 수와 예상 효과를 알 수 있다.
- **SC-005**: 정리 직후 재실행은 삭제 0건을 보고하고, 통계 수치와 실제 DB 상태가 일치한다.

## Assumptions

- 단일 사용자 데스크톱 앱이며, 정리 중 다른 프로세스가 DB에 쓰지 않는다.
- 통계 화면의 저장소 지표(전체 기사 수·범위 수 등) 표시 위치는 이미 존재하며, 그곳에 사용하지 않는 범위 수와 정리 진입점을 둔다.
- 범위 동일성은 저장된 정규형 키의 정확 일치로 판단한다(퍼지 매칭 없음).
- 삭제 표시 행의 보존·회수 정책(기본 90일)은 기존 정책이 관장하며 본 기능 범위 밖이다.
- 자동 정리(스케줄·주기적 실행)는 본 기능 범위 밖이다. 수동 실행만 제공한다.
- 클라우드 동기화와의 상호작용은 삭제 표시 행을 건드리지 않는 선에서 없으며, 별도 동기화 처리를 추가하지 않는다.
- 대상 범위 이름 표시는 저장된 키워드 표시값을 그대로 사용한다.
